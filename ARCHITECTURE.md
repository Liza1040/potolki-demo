## 1. Что это за проект

Одностраничный лендинг с квизом под трафик из Яндекс.Директа. Вымышленная
компания «Потолки Первый Метр», Москва. Задача лендинга — получить заявку,
сняв три возражения клиента (они перечислены в `BRIEF.md`).

Технически это **статически сгенерированный сайт** с одним динамическим
эндпоинтом для приёма заявок. Никакой базы данных, никакой авторизации,
никакой CMS.

Ключевые характеристики:

- 4 страницы: главная, `/privacy`, `/consent`, 404
- 1 API-маршрут: `POST /api/lead`
- 0 внешних runtime-зависимостей (кроме `next`, `react`, `react-dom`)
- Lighthouse mobile: Performance 98, Accessibility 100, Best Practices 100, SEO 100

## 2. Next.js App Router: теория, которая нужна дальше

### Что такое App Router

Next.js — фреймворк поверх React. Начиная с 13-й версии в нём есть
**App Router**: маршруты описываются структурой папок внутри `app/`.

```
app/page.tsx          → /
app/privacy/page.tsx  → /privacy
app/api/lead/route.ts → /api/lead
```

Специальные имена файлов зарезервированы под роли:

| Файл | Роль |
|---|---|
| `page.tsx` | страница по этому адресу |
| `layout.tsx` | обёртка вокруг страниц, не размонтируется при навигации |
| `not-found.tsx` | что показать при 404 |
| `route.ts` | HTTP-эндпоинт вместо страницы |
| `sitemap.ts` / `robots.ts` / `manifest.ts` | генерируют одноимённые файлы |
| `opengraph-image.tsx` | генерирует картинку-превью |
| `icon.svg` / `apple-icon.png` / `favicon.ico` | иконки, подхватываются автоматически |

Все эти соглашения в проекте используются — руками в `<head>` мы ничего
не пишем.

### Server Components и Client Components — главное различие

Это самая важная концепция, от неё зависит половина решений в проекте.

**По умолчанию каждый компонент в App Router — серверный.** Он выполняется
только на сервере (при сборке или при запросе), его код **не попадает
в JavaScript-бандл браузера**. В браузер приезжает уже готовый HTML.

Серверный компонент не может:
- использовать `useState`, `useEffect` и другие хуки состояния
- вешать обработчики `onClick`
- обращаться к `window` и `document`

**Клиентский компонент** объявляется директивой `"use client"` в первой
строке файла. Его код едет в браузер, он гидратируется (React «оживляет»
готовый HTML, навешивая обработчики) и умеет всё вышеперечисленное.

В нашем проекте клиентских компонентов ровно два дерева:

```
components/sections/QuizSection.tsx  "use client"  → тянет за собой quiz/*
components/sections/FinalCta.tsx     "use client"  → тянет lib/phone
```

Всё остальное — hero, цены, отзывы, FAQ, футер — **серверное**. Поэтому
JS-бандл маленький, а FAQ работает даже с отключённым JavaScript.

### Граница server → client: что через неё проходит

Когда серверный компонент передаёт пропсы клиентскому, эти пропсы
**сериализуются** — превращаются в поток данных, который потом восстановится
в браузере. Через границу проходят: строки, числа, булевы, массивы, простые
объекты, `Date`, `Map`, `Set`, JSX.

**Не проходят: функции и классы.**

Это не абстрактное ограничение — мы на него напоролись. Изначально правила
валидации квиза были функциями:

```ts
// так БЫЛО — и сборка падала
validate: (raw) => raw.length >= 2 ? null : "Слишком коротко"
```

Сборка упала с ошибкой `Functions cannot be passed directly to Client
Components`. Пришлось переписать валидацию как **данные**:

```ts
// так СТАЛО
rules: [{ kind: "minLength", value: 2, message: "Слишком коротко" }]
```

Функция, которая эти правила исполняет, живёт уже внутри клиентского кода
(`components/quiz/validation.ts`). Побочный эффект оказался полезным:
конфиг квиза стал полностью декларативным и его можно хоть из JSON читать.

По той же причине шаблоны текстов — строки с плейсхолдерами, а не колбэки:

```ts
progress: "Шаг {current} из {total}"   // а не (c, t) => `Шаг ${c} из ${t}`
```

Подставляет значения функция `fillTemplate` на клиенте.

### Как это собирается

`npm run build` запускает **пререндер**: Next выполняет серверные компоненты
и сохраняет готовый HTML. При запросе пользователь получает статический файл —
сервер ничего не вычисляет. В выводе сборки это помечено значком `○ (Static)`.

Динамический только `/api/lead` — он помечен `ƒ (Dynamic)`, потому что должен
выполняться на каждый запрос.

## 4. Принцип №1: контент отдельно от разметки

### Правило

**В JSX не должно быть ни одной русской строки.** Все тексты лежат
в `content/`, компонент получает свой кусок пропсом:

```tsx
<Hero content={content.hero} />
```

Компонент секции никогда не импортирует `content/` сам.

### Зачем

1. **Переиспользование.** Секцию можно перенести в другой проект, подсунув
   другой контент. Это прямая подготовка к `kit/`.
2. **Перестановка блоков.** Порядок секций меняется в одном файле `page.tsx`.
3. **Правка текстов без риска.** Клиент просит поменять формулировку —
   вы правите один объект, не трогая разметку.
4. **Видно, что вообще написано.** Все тексты лендинга читаются подряд,
   как документ.

Правило нарушалось дважды по невнимательности (подписи колонок в карточках
цен, заголовки колонок футера) — оба раза выносили в контент.

### Как типизировано

Все типы — в `content/types.ts`. Объекты помечены `satisfies`:

```ts
export const hero = { ... } satisfies HeroContent;
```

**Почему `satisfies`, а не `: HeroContent`.** Аннотация типа расширяет тип
значения до объявленного: literal `"matte"` станет `string`. `satisfies`
проверяет соответствие, но **сохраняет узкие литеральные типы**. Благодаря
этому из `content/prices.ts` выводятся точные объединения:

```ts
export type TextureId = (typeof TEXTURES)[number]["id"];
// "matte" | "satin" | "gloss" | "fabric", а не string
```

## 5. Принцип №2: единые источники правды

Два файла, которые нельзя дублировать.

### `content/prices.ts` — деньги

Хранит ставки ₽/м² по фактурам и множители сложности помещений.

Читают: расчёт квиза (`lib/estimate.ts`), таблица цен, карточка цены
в hero, ответ в FAQ, `description` в метатегах.

**Почему это важно.** Цифра 390 ₽ изначально была написана в четырёх местах.
Через месяц правки прайса они бы разошлись, и квиз считал бы одно, а таблица
показывала другое. Для лендинга, который обещает «цена не меняется», это
провал не технический, а смысловой.

Сейчас правка одной строки в `prices.ts` меняет цифры везде, включая
сниппет в поисковой выдаче.

### `content/business.ts` — факты о компании

Телефон, адрес, координаты, часы работы, реквизиты, мессенджеры.

Читают: шапка, футер, метатеги, LocalBusiness JSON-LD, тексты ошибок в формах
(«позвоните сами: …»), юридические страницы.

До рефакторинга телефон был захардкожен в **шести файлах**. Проверка
«телефон кликабельный везде» такое не ловит — она проверяет только то,
что показано, а не то, что показано одинаково.

**Часы работы и адрес намеренно хранятся в двух формах:**

```ts
hours: {
  human: "Замеры и монтаж ежедневно с 9:00 до 21:00",  // для людей
  schemaSpec: "Mo-Su 09:00-21:00",                      // для поисковика
  opens: "09:00", closes: "21:00",                      // для JSON-LD
}
```

Это не дублирование, а два представления одного факта. Лежат рядом,
чтобы правились вместе.

### Реквизиты: контрольные разряды

ИНН и ОГРН вымышленные, но **проходят проверку по алгоритму** — их считали,
а не выдумывали.

- **ИНН (10 знаков).** Первые 9 цифр умножаются на веса
  `[2,4,10,3,5,9,4,6,8]`, сумма берётся по модулю 11, потом по модулю 10 —
  получается контрольная цифра. Для `772456130` → 0, поэтому ИНН
  `7724561300`.
- **ОГРН (13 знаков).** Первые 12 цифр как число делятся на 11, остаток
  по модулю 10 даёт 13-ю цифру. Для `116774659832` → 6, отсюда
  `1167746598326`.

Изначальные значения (`...308` и `...321`) проверку не проходили. Любой
бухгалтер или онлайн-валидатор это заметит, и доверие к сайту падает.

## 6. Движок квиза

Самая сложная часть проекта и главный кандидат на переезд в `kit/`.

### Разделение движка и конфига

```
components/quiz/          движок — не знает слова «потолок»
  types.ts                типы шагов, состояния, действий
  reducer.ts              состояние и переходы
  validation.ts           исполнение правил + подстановка в шаблоны
  Quiz.tsx                главный компонент
  ProgressBar.tsx
  steps/
    ChoiceStepView.tsx    шаг выбора
    NumberStepView.tsx    шаг числового ввода
    FormStepView.tsx      шаг формы

content/quiz.ts           конфиг — описание шагов конкретного квиза
components/sections/QuizSection.tsx   предметная обвязка: расчёт и отправка
lib/estimate.ts           формула расчёта
```

Добавить пятый шаг в другом проекте = дописать объект в массив `steps`.
Движок не трогается.

### Типы шагов: дискриминированное объединение

```ts
export type QuizStep = ChoiceStep | NumberStep | FormStep;
```

У каждого варианта есть поле-дискриминатор `kind`. Это стандартный приём
TypeScript: когда вы проверяете `if (step.kind === "number")`, компилятор
**сужает** тип и внутри блока даёт доступ к `step.min`, `step.max`, `step.presets` —
полям, которых нет у других вариантов. Опечатка или забытый вариант
превращаются в ошибку компиляции, а не в баг в проде.

### Состояние: `useReducer`

```ts
export interface QuizState {
  stepIndex: number;
  answers: Answers;
  errors: Record<string, string>;
  status: "idle" | "loading" | "success" | "error";
  started: boolean;
}
```

**Теория.** `useReducer` — второй способ хранить состояние в React,
помимо `useState`. Вместо набора отдельных переменных вы держите один
объект и меняете его через **действия** (`{ type: "next" }`), которые
обрабатывает чистая функция-редьюсер: `(состояние, действие) → новое состояние`.

**Почему здесь он, а не `useState`.** Пять взаимозависимых величин.
Переход «далее» должен одновременно провалидировать шаг, записать или
очистить ошибки и, если всё хорошо, сдвинуть индекс. На `useState` это
три вызова подряд с риском рассинхрона. В редьюсере это один переход,
описанный в одном месте.

**Почему не библиотека форм.** Четыре шага и три поля не окупают
`react-hook-form` + `zod` (~30 КБ) и второй способ описывать валидацию.

Редьюсер создаётся фабрикой, замкнутой на конфиг:

```ts
const reducer = useMemo(() => createQuizReducer(config), [config]);
```

Так редьюсер остаётся чистой функцией, но знает про шаги.

### Валидация: правила как данные

```ts
export type ValidationRule =
  | { kind: "required"; message: string }
  | { kind: "minLength"; value: number; message: string }
  | { kind: "phone"; message: string };
```

Причина такого решения — граница server/client (см. раздел 2). Исполняет
правила `validateValue()`, возвращая текст первой сработавшей ошибки.

**Когда показываются ошибки.** Только по нажатию «Далее» или «Отправить»,
не во время ввода. Подсветить поле красным, пока человек ещё печатает
первую букву, — верный способ его разозлить. Как только поле исправили,
ошибка гаснет: `dispatch({ type: "answer" })` удаляет запись из `errors`.

### Поведение шагов

- **Автопереход** на шагах выбора: после клика ждём 320 мс (чтобы выбор
  было видно), потом переходим. Таймер лежит в `useRef` и снимается
  в `useEffect`-cleanup и при ручной навигации — иначе переход сработал бы
  после того, как пользователь уже нажал «Назад».
- **Назад** ответы не чистит: вернулся, поправил, пошёл дальше.
- **Далее** заблокирована, пока шаг не заполнен корректно.
- **Высота** контейнера зафиксирована `min-h-[24rem]` — при смене шага
  кнопки не прыгают под пальцем.
- **Анимация** — один короткий `fade + translateY` 220 мс, отключается
  при `prefers-reduced-motion`.

### Доступность

- Варианты — настоящие `<input type="radio">`, спрятанные через `sr-only`,
  а не `<div onClick>`. Работают стрелки, `Tab`, скринридер.
- Смена шага объявляется через `aria-live="polite"` в скрытом параграфе.
- Фокус переносится на заголовок нового шага (`tabIndex={-1}` + `.focus()`),
  но **не на первом рендере** — иначе страница прыгнула бы к квизу
  при загрузке.
- Прогресс-бар: `role="progressbar"` + `aria-label` + `aria-valuenow`.
  Отсутствие `aria-label` поймал Lighthouse — было реальным нарушением.

### Расчёт стоимости

`lib/estimate.ts`, чистая функция:

```
база   = ставка_фактуры × множитель_помещения × площадь
вилка  = база ± 10%, округление до сотен
```

Показывается **до формы контактов** на том же шаге: человек видит ценность
раньше, чем отдаёт телефон. Вилка, а не точная сумма — потому что точную
назовёт замерщик, и обещать её на сайте нельзя.

## 7. Формы и приём заявок

### Две формы, один эндпоинт

| Форма | `source` | Что отправляет |
|---|---|---|
| Квиз | `quiz` | имя, телефон, ответы шагов, вилка расчёта |
| Короткая внизу | `final-form` | имя, телефон |

Поле `source` позволяет клиенту видеть, какой сценарий приносит заявки.

### Route Handler: теория

`app/api/lead/route.ts` — это **Route Handler**, серверный обработчик
HTTP-запроса. Экспортируемая функция называется по методу:

```ts
export async function POST(request: Request): Promise<NextResponse> { ... }
```

Работает на сервере, в браузер не попадает, поэтому в нём безопасно
обращаться к секретам из `process.env`.

### Валидация на сервере

Клиентской валидации доверять нельзя: запрос можно отправить руками через
`curl`, минуя интерфейс. Поэтому `parseLead()` проверяет всё заново:

```ts
const PHONE_PATTERN = /^\+7\d{10}$/;
if (name.length < 2 || name.length > 60) return null;
if (!PHONE_PATTERN.test(phone)) return null;
```

Невалидный запрос → `400`, ошибка Telegram → `502`, успех → `{ ok: true }`.

### Отправка в Telegram

Используется Bot API — HTTP-метод `sendMessage`:

```
POST https://api.telegram.org/bot<ТОКЕН>/sendMessage
{ "chat_id": "...", "text": "..." }
```

**Если переменных окружения нет** — заявка пишется в лог сервера и
возвращается успех. Это сознательное решение: демо должно работать
у любого, кто склонировал репозиторий, без настройки бота.

Идентификаторы ответов расшифровываются человеческими названиями через
`findRoom`/`findTexture` из `prices.ts` — в чат приходит «Матовый»,
а не `matte`.

### Маска телефона

`lib/phone.ts`, без библиотеки.

```
extractDigits  "+7 (916) 123" → "916123"   (отбрасывает 7/8 в начале)
formatPhone    "9161234567"   → "+7 (916) 123-45-67"
applyPhoneMask реформатирование при вводе
isValidPhone   ровно 10 цифр
toE164         "+79161234567" для отправки
```

**Неочевидный момент, который стоил бага.** Если пользователь стёр символ
маски — например скобку — набор цифр не изменился, и `formatPhone` вернёт
ту же строку. Визуально `Backspace` «залипает». Решение: сравнить наборы
цифр до и после, и если они совпали при уменьшении длины строки — удалить
последнюю цифру:

```ts
if (isDeleting && nextDigits === extractDigits(previous)) {
  return formatPhone(nextDigits.slice(0, -1));
}
```

Баг нашёлся автотестом, а не глазами.

### Состояния и защита от двойной отправки

`idle → loading → success | error`. Повторный вызов при `status === "loading"`
отсекается в самом начале обработчика. При ошибке **введённые данные
остаются** — человеку не нужно набирать телефон заново.

Экран успеха не говорит «спасибо», а объясняет, что произойдёт дальше
и в какой срок: перезвоним за 15 минут в рабочее время, ночные заявки —
утром.

## 8. Стилизация: Tailwind CSS v4

### Что такое Tailwind и что изменилось в v4

Tailwind — CSS-фреймворк утилитарных классов: вместо своих классов
и отдельного CSS-файла вы пишете `flex items-center gap-3` прямо в разметке.
Сборщик собирает только те утилиты, которые реально встретились в коде.

**В v4 конфигурация переехала из `tailwind.config.js` в CSS.** Токены темы
объявляются директивой `@theme` прямо в `globals.css`:

```css
@theme {
  --color-brand: #1d4ed8;
  --color-cta: #f59e0b;
  --font-sans: var(--font-manrope), ui-sans-serif, system-ui, sans-serif;
  --radius-card: 1rem;
}
```

Из каждой переменной Tailwind **сам генерирует утилиты**: `--color-brand`
даёт `bg-brand`, `text-brand`, `border-brand`; `--radius-card` даёт
`rounded-card`. Отдельного конфига в проекте нет вообще.

Правило: цвета в разметке — только через токены. Никаких `bg-[#1d4ed8]`.

### Грабли: конфликт утилит display

Кнопка в шапке имела классы `hidden lg:inline-flex`, но на мобильном
всё равно показывалась и ломала вёрстку.

Причина: в компоненте `Button` базовый класс содержит `inline-flex`,
и он оказался **позже в CSS-файле**. Конфликт двух утилит одного свойства
решается порядком правил в стилях, а **не порядком слов в атрибуте
`class`**. Внешний `hidden` проигрывал.

Решение — прятать обёрткой:

```tsx
<span className="hidden lg:block">
  <Button ... />
</span>
```

В `Button.tsx` над базовыми классами оставлен предупреждающий комментарий.
Это общая ловушка Tailwind при компонентах с зашитыми классами; в больших
проектах её решают через `tailwind-merge`, но ради одного случая тянуть
зависимость незачем.

### Мобильный вид первичен

Базовые классы описывают мобильный экран, префиксы `sm:`/`lg:` добавляют
десктоп. Проверка идёт от 360 px. Ключевое требование:
`document.documentElement.scrollWidth === window.innerWidth` — горизонтального
скролла быть не должно.

Важно: раньше в `body` стоял `overflow-x: hidden`. Он **прятал** проблему,
а не решал её. Убран намеренно, чтобы тесты видели реальные переполнения.

### Таблица цен на мобильном

Требование «таблица не должна ехать» решено не скроллом, а сменой
представления: на `lg` и выше рендерится настоящая `<table>`, ниже — карточки.
Оба варианта берут данные из одного массива, дублируется только разметка.

## 9. Шрифты: next/font

### Как это работает

```ts
const manrope = Manrope({
  subsets: ["cyrillic", "latin"],
  weight: ["400", "500", "700", "800"],
  display: "swap",
  variable: "--font-manrope",
});
```

`next/font/google` **скачивает шрифт на этапе сборки** и кладёт его в
статику проекта. В рантайме запросов к `fonts.googleapis.com` нет вообще.
Что это даёт:

- нет обращения к стороннему домену → нет лишнего DNS + TLS на критическом пути
- нет зависимости от доступности Google (в РФ существенно)
- Next сам добавляет `<link rel="preload">` для файлов шрифта

**`display: "swap"`** — пока шрифт грузится, текст рисуется системным
шрифтом и потом подменяется. Альтернатива `block` дала бы невидимый текст
на старте (FOIT), что хуже и для восприятия, и для FCP.

**Про CLS.** Подмена шрифта обычно двигает вёрстку, потому что метрики
шрифтов различаются. `next/font` автоматически считает `size-adjust`,
`ascent-override` и другие дескрипторы для запасного шрифта, подгоняя его
метрики под целевой. Результат — **CLS = 0** в замерах, при том что
подмена шрифта реально происходит.

### История про лишний вес

В коде использовался класс `font-semibold` (вес 600) в 12 местах,
но вес 600 в список загружаемых не входил. Браузер в таком случае
**синтезирует** начертание из соседнего — текст выглядит чуть грязнее
и толще, чем задумано.

Варианта было два: добавить 600 в сборку (+файл шрифта на каждый субсет)
или свести к уже загруженному 700. Все 12 мест — мелкие подписи 13–14 px,
где разница между 600 и 700 неразличима. Заменили на `font-bold`:
рендеринг стал честным, вес сборки не вырос.

**Проверить, что все используемые веса загружены:**

```bash
grep -rho "font-\(medium\|semibold\|bold\|extrabold\)" components/ app/ | sort | uniq -c
```

Сейчас загружаются 400 (базовый текст), 500, 700, 800 — ровно те, что
встречаются в коде.

## 10. SEO-обвязка

### Metadata API

Метатеги описываются экспортом объекта, а не разметкой в `<head>`:

```ts
export const metadata: Metadata = {
  metadataBase: new URL(meta.siteUrl),
  title: meta.title,
  description: meta.description,
  alternates: { canonical: "/" },
  openGraph: { type: "website", locale: "ru_RU", ... },
  twitter: { card: "summary_large_image", ... },
};
```

`metadataBase` — базовый адрес, от которого достраиваются относительные
ссылки (`canonical: "/"` превращается в полный URL). Берётся из
`NEXT_PUBLIC_SITE_URL`; если переменная не задана, подставляется заглушка
`https://pervyi-metr.example` — **на боевом деплое переменную обязательно
задать**, иначе canonical и OG будут указывать в никуда.

### Длины title и description

- **title — 49 символов.** Ограничение ~60: длиннее обрезается многоточием.
  Формула: оффер + гео + цена.
  `Натяжные потолки в Москве за 1 день — от 390 ₽/м²`
- **description — 160 символов.** Этот текст почти целиком попадает
  в сниппет выдачи, поэтому в нём цена, срок, гарантия и гео.

Цифра цены подставляется из `prices.ts`, поэтому при правке прайса
изменится и сниппет.

### sitemap.xml и robots.txt

Оба генерируются кодом (`app/sitemap.ts`, `app/robots.ts`), а не лежат
статикой — адрес сайта берётся из переменной окружения, и файлы не
приходится править руками при смене домена.

**Тонкость с юридическими страницами.** `/privacy` и `/consent` помечены
`robots: { index: false }` в своих метаданных и **не включены в sitemap**.
При этом в `robots.txt` они **не запрещены** — и это намеренно: если
запретить обход, робот не сможет прочитать метатег `noindex` и в некоторых
случаях покажет страницу в выдаче вообще без описания. Правильный порядок:
разрешить обход, запретить индексацию метатегом.

### Микроразметка JSON-LD

Две схемы, обе рендерятся серверно:

**`FAQPage`** (`components/sections/Faq.tsx`) — строится из того же массива
вопросов, что и видимый аккордеон, поэтому текст в схеме и на странице
не может разойтись. Даёт шанс на раскрывающиеся вопросы прямо в выдаче.

**`HomeAndConstructionBusiness`** (`components/seo/LocalBusinessJsonLd.tsx`) —
подтип `LocalBusiness`: название, телефон, адрес, координаты, зона
обслуживания радиусом 30 км, часы работы, диапазон цен, год основания.
Все поля берутся из `business.ts` и `prices.ts`.

Проверять готовые схемы: [валидатор Яндекса](https://webmaster.yandex.ru/tools/microtest/)
и [Rich Results Test](https://search.google.com/test/rich-results).

### Иерархия заголовков

Ровно один `<h1>` на страницу, уровни без пропусков (`h1 → h2 → h3`).
Проверяется автотестом на всех четырёх страницах. Пропуск уровня —
не косметика: скринридеры строят по заголовкам оглавление документа.

## 11. OG-картинка: генерация кодом

### Зачем

Ссылку на лендинг первым делом кидают в Telegram или WhatsApp. Превью
видят раньше самого сайта. Дефолтное превью без картинки выглядит как
недоделанная работа.

### Как устроено

`app/opengraph-image.tsx` возвращает `ImageResponse` — это API, за которым
стоит библиотека **satori**. Она принимает JSX с подмножеством CSS
(flexbox, абсолютное позиционирование, градиенты) и превращает его
в SVG, а затем в PNG.

Ограничения satori, о которые легко споткнуться:

- нет `display: block` — только `flex`; каждому контейнеру с несколькими
  детьми нужен явный `display: "flex"`
- нет внешних картинок без явной загрузки
- шрифты нужно передавать буфером

### Два решения, которые стоит запомнить

**1. Картинка генерируется на сборке, а не в рантайме.** Страница
статическая, поэтому Next вычисляет `opengraph-image` один раз при
`npm run build` и кладёт готовый PNG в бандл. В выводе сборки видно
`○ /opengraph-image` — значок статики. Каждый шер ссылки не дёргает сервер.

**2. Шрифт читается из репозитория, а не из сети:**

```ts
const fontsDir = join(process.cwd(), "assets", "fonts");
const manropeBold = readFileSync(join(fontsDir, "Manrope-ExtraBold.ttf"));
```

Причины две. Первая: у satori **дефолтный шрифт не покрывает кириллицу** —
вместо букв были бы прямоугольники. Вторая: если тянуть шрифт с Google
на этапе сборки, сборка станет зависеть от сети и однажды упадёт на деплое.

Поэтому в `assets/fonts/` лежат два TTF — **их обязательно коммитить**.
Это единственные бинарные файлы шрифтов в репозитории; сам сайт использует
шрифт через `next/font`, а не отсюда.

### Проверка

```bash
curl -I http://localhost:3000/opengraph-image   # 200, image/png
```

Картинку проверяли и в масштабе превью (~300 px шириной): оффер и цена
читаются, по краям ничего не обрезано. Результат — `docs/og-preview.png`.

## 12. Иконки и манифест

| Файл | Назначение |
|---|---|
| `app/icon.svg` | favicon для современных браузеров, векторный |
| `app/favicon.ico` | запасной вариант для старых клиентов и краулеров |
| `app/apple-icon.png` | 180×180, иконка на домашнем экране iOS |
| `public/icon-192.png`, `icon-512.png` | для веб-манифеста и Android |
| `app/manifest.ts` | манифест: имя, цвета, иконки |

Next подхватывает `icon.*`, `apple-icon.*` и `favicon.ico` по имени файла
и сам добавляет теги в `<head>`.

**Как сделан `.ico`.** Формат ICO — это контейнер: 6-байтный заголовок,
16-байтная запись о картинке, затем данные. Начиная с Windows Vista внутрь
можно положить **PNG как есть**, не конвертируя в BMP. Скрипт рендерит
SVG в PNG 32×32 через headless-браузер и оборачивает результат в этот
контейнер вручную — без графических библиотек. Скрипт лежит в
`scratchpad/make-icons.mjs`, запускать его повторно нужно только при
смене логотипа.

Знак — монограмма «М» с фирменной точкой. На 16–32 px однобуквенный знак
разборчивее, чем «1м» из шапки.

## 13. Аналитика

### Обёртка

`lib/analytics.ts` — единственная точка, через которую уходят события:

```ts
export type AnalyticsEvent =
  | { name: "quiz_start" }
  | { name: "quiz_step_complete"; step: number; stepId: string }
  | { name: "quiz_submit" }
  | { name: "form_submit"; source: "quiz" | "final-form" };

export function track(event: AnalyticsEvent): void
```

Тип — объединение с дискриминатором, поэтому опечатка в названии цели
или забытый параметр не компилируются.

**Если счётчик не задан, `track` молча ничего не делает** (в dev пишет
в консоль). Поэтому вызывать её можно откуда угодно без проверок,
и демо работает без аналитики.

### Подключение

`components/analytics/YandexMetrika.tsx`. Если `METRIKA_ID === null` —
компонент возвращает `null`, скрипт не грузится, запросов нет.

**Стратегия загрузки.** `next/script` умеет:

| Стратегия | Когда грузится |
|---|---|
| `beforeInteractive` | до гидратации, блокирует |
| `afterInteractive` | сразу после гидратации ← наш выбор |
| `lazyOnload` | в простое, после всех ресурсов |

Взяли `afterInteractive`: скрипт вне критического пути рендера и не портит
LCP, но при этом не теряет визиты тех, кто закрыл вкладку через пару секунд
(а `lazyOnload` их бы потерял).

Дополнительно оставлен `<noscript>` с пикселем: часть трафика из Директа
приходит с отключённым JS, без пикселя эти визиты не считаются.

### Проверка, что цели долетают

Тест `scratchpad/metrika-test.mjs` подменяет `window.ym` **до загрузки
страницы** (сниппет Метрики использует `m[i] = m[i] || function(){}`,
поэтому заглушка сохраняется), проходит квиз и форму и проверяет вызовы.
Запросы к `mc.yandex.ru` перехватываются и не уходят наружу.

Подтверждено: `quiz_start`, `quiz_step_complete` (с номером шага),
`quiz_submit`, `form_submit` (с `source`).

## 14. Производительность: разбор кейса 50 → 98

Показательная история — стоит прочитать целиком, метод применим к любому
проекту.

### Что было

Первый замер на продакшен-сборке, мобильный пресет:

```
Performance 50   LCP 4.3 s   TBT 1430 ms   CLS 0
```

### Как искали причину

Смотрели не общий балл, а **разбивку работы главного потока**:

```
Style & Layout            3310 ms   ← вот оно
Script Evaluation         1245 ms
Other                      825 ms
Rendering                  201 ms
Parse HTML & CSS           169 ms
```

Дальше — фазы LCP:

```
TTFB          174 ms   4 %
Render Delay  4091 ms  96 %   ← отрисовка, а не сеть
```

Сеть и сервер ни при чём. Всё упиралось в стили: 3.3 секунды на пересчёт
и раскладку при том, что страница весит 256 КБ и не содержит изображений.

### Причина

Два CSS-свойства:

1. **`blur-3xl`** (`filter: blur(64px)`) на декоративном круге 520×520 px
   в первом экране.
2. **`backdrop-blur`** на липкой шапке.

**Теория.** `filter` и `backdrop-filter` выносят элемент на отдельный
композиторский слой и заставляют браузер растрировать его заново. Размытие
по Гауссу с большим радиусом — дорогая операция, а `backdrop-filter`
пересчитывается при каждом изменении того, что под ним, то есть на каждый
кадр скролла. На мобильном процессоре (Lighthouse эмулирует замедление
в 4 раза) это выливается в секунды.

### Что сделали

| Было | Стало |
|---|---|
| круг 520 px с `filter: blur(64px)` | `radial-gradient` в фоне секции |
| `backdrop-blur` на шапке | сплошной белый фон |
| `text-balance` на мелких подписях | оставлен только на заголовках |

Радиальный градиент рисуется движком фона практически бесплатно и выглядит
так же. `text-wrap: balance` требует нескольких проходов раскладки —
на заголовках это оправдано, на 15-пиксельных подписях нет.

### Результат

```
                до      после
Performance     50   →   98
LCP           4.3 s  →  2.2 s
TBT          1430 ms →  70 ms
Style & Layout 3310  →  281 ms
```

Ни одна метрика не «подгонялась» — правки уменьшили реальную работу
браузера, а внешний вид не изменился.

### Отдельная ловушка при замерах

Первые прогоны показывали ошибки 500 в консоли и странные результаты.
Причина: старый процесс `npm start` держал порт и отдавал HTML от прежней
сборки, у которой имена JS-чанков уже не совпадали с новыми файлами.

**Правило: после `npm run build` обязательно перезапускать `npm start`.**
Иначе замеряете смесь двух сборок.

### Почему CLS = 0

Совокупный сдвиг макета нулевой не случайно:

- у квиза зафиксирована минимальная высота — смена шага не двигает кнопки
- `next/font` подгоняет метрики запасного шрифта, подмена не двигает текст
- изображений на первом экране нет вообще
- в галерее работ у плиток задан `aspect-[4/3]` — место под фото
  зарезервировано до его загрузки

## 15. Доступность

Итог: **100 баллов Lighthouse**. Что сделано осознанно:

- **Семантика.** `<ol>` для шагов процесса, `<table>` для таблицы цен,
  `<details>/<summary>` для FAQ, `<nav aria-label>` для обеих навигаций.
- **Клавиатура.** Всё интерактивное достижимо табом; видимый фокус задан
  глобально через `:focus-visible` с `outline`.
- **Размер целей.** Кнопки и поля — минимум 44–48 px по высоте.
- **Формы.** У каждого поля `<label for>`, ошибки связаны через
  `aria-describedby`, невалидные поля помечены `aria-invalid`.
  Ошибка отправки объявляется через `role="alert"`.
- **FAQ на нативных `<details>`.** Раскрытие с клавиатуры, объявление
  состояния и работа без JS — бесплатно, без единой строки JavaScript
  и без `aria-expanded` руками.
- **`prefers-reduced-motion`** отключает анимацию смены шагов и плавный
  скролл.

### Два реальных бага, которые нашёл Lighthouse

1. **`role="progressbar"` без имени.** Скринридер объявлял «индикатор
   выполнения» без указания, к чему он относится. Добавлен `aria-label`.

2. **Недостаточный контраст в четырёх местах.** Цифры считали, а не
   подбирали на глаз:

   | Элемент | Было | Стало | Порог |
   |---|---|---|---|
   | номера шагов, `text-brand/25` | 1.49 | 3.57 (`/70`) | 3:1 (крупный текст) |
   | надзаголовок на синем, `text-white/70` | 4.10 | 5.28 (`/85`) | 4.5:1 |
   | дисклеймер в футере, `text-white/40` | 3.79 | 6.05 (`/55`) | 4.5:1 |

   **Теория.** Контраст считается как отношение относительных яркостей:
   `(L_светлее + 0.05) / (L_темнее + 0.05)`. Яркость канала считается
   не линейно, а с гамма-коррекцией. WCAG AA требует 4.5:1 для обычного
   текста и 3:1 для крупного (от 18.66 px жирного или 24 px обычного).
   Полупрозрачный цвет предварительно смешивается с фоном.

## 16. Тестирование

Отдельного тест-раннера в проекте нет — проверки написаны как скрипты
на `puppeteer-core`, который управляет установленным Chrome.
Лежат в `tests/`, инструкция по запуску — в `tests/README.md`.

| Скрипт | Что проверяет |
|---|---|
| `preflight.mjs` | консоль без ошибок, отсутствие `console.log`, один `h1` и иерархия заголовков на 4 страницах, битые ссылки и якоря, кликабельность телефона, 404, работа без JS, метатеги и их длины, обе JSON-LD схемы, ширины 360/768/1440 |
| `full-page-test.mjs` | сценарии квиза и формы целиком: автопереход, сохранение ответов при возврате, валидация, маска, расчёт вилки, отправка, `source`, доступность FAQ с клавиатуры |
| `metrika-test.mjs` | долёт целей в Метрику при заданном ID |
| `shot-*.mjs` | скриншоты секций на трёх ширинах |
| `make-icons.mjs` | генерация иконок и `.ico` |

Итог последнего прогона: **34 + 30 проверок, ни одного провала**.

### Чему научил опыт написания тестов

**Клик по координатам может перехватить липкая шапка.** Пустая отправка
формы «не показывала ошибки» — на деле `page.click()` попадал в шапку.
Диагностируется заменой на DOM-клик:

```js
await page.$eval("#zayavka button[type=submit]", (b) => b.click());
```

**Нужно дожидаться гидратации.** До неё клик по кнопке отправки уходит
нативным сабмитом формы и перезагружает страницу. Проверка:

```js
await page.waitForFunction(() => {
  const el = document.querySelector("#zayavka input[name=name]");
  return el && Object.keys(el).some((k) => k.startsWith("__react"));
});
```

**Headless Chrome с `--window-size=360` не эмулирует мобильный вьюпорт**,
а просто обрезает кадр. Нужен `page.setViewport({ width, height, isMobile })`.

## 17. Узкие места и как их закрывать

Честный список того, что в проекте не сделано или сделано с ограничениями.

### 1. Секция «Работы» без фотографий

**Состояние.** Компонент `components/sections/Works.tsx` готов, тексты
и подписи в `content/works.ts` написаны, но секция **не смонтирована**
в `page.tsx`, а пункт «Работы» убран из навигации — чтобы ссылка не вела
в пустоту.

**Что нужно.** Шесть файлов `public/images/works/work-1..6.webp`,
1200×900 (4:3), интерьеры после ремонта. Требования по каждому слоту —
в истории задачи и в `content/works.ts`.

**Как включить.** Положить файлы → добавить `<Works content={content.works} />`
в `page.tsx` между `Pricing` и `Reviews` → вернуть пункт в `content/header.ts`.

### 2. `/api/lead` без защиты от спама

**Проблема.** Эндпоинт открыт: скриптом можно залить чат заявками.
Для демо не критично, для боевого проекта — да.

**Варианты решения по возрастанию сложности:**
- honeypot: скрытое поле, которое заполняют только боты, — 20 минут работы;
- ограничение частоты по IP (для Vercel — Upstash Redis или Vercel KV);
- Yandex SmartCaptcha — но она добавляет трение в воронку, ставить
  только если спам реально пошёл.

### 3. Telegram — единственный канал, без ретраев

**Проблема.** Если Telegram недоступен, заявка теряется: пользователь
увидит ошибку, а записи нигде не останется.

**Решения.** Минимум — дублировать на почту. Правильно — писать заявку
в хранилище (Vercel KV, Google Sheets, CRM) до отправки в мессенджер,
чтобы канал доставки не был единственным местом хранения.

### 4. Состояние квиза не переживает перезагрузку

Решение осознанное: `sessionStorage` добавил бы синхронизацию и крайние
случаи ради редкого сценария. Если аналитика покажет, что люди уходят
и возвращаются на середине квиза, — добавить сохранение в `sessionStorage`
по `stepIndex` и `answers`.

### 5. Тесты не подключены к CI

Скрипты лежат в `tests/`, но запускаются руками и требуют отдельной
установки `puppeteer-core` в этой папке. Для проекта, который будут
развивать, стоит поднять их в основной `package.json` как dev-зависимость
и добавить `npm run check`, запускающий проверки против `npm start`.

### 6. Реквизиты и отзывы вымышленные

Реквизиты валидны по формату, но принадлежат несуществующей организации.
Отзывы написаны, а не собраны. **Перед сдачей боевого проекта заменить
обязательно** — в `content/business.ts` и `content/reviews.ts`.

### 7. `NEXT_PUBLIC_SITE_URL` обязателен на проде

Без него canonical, OG-ссылки, sitemap и robots будут указывать на
`https://pervyi-metr.example`. Сайт откроется и будет работать, но
поисковики получат мусорные адреса. Переменные окружения на Vercel
применяются **на сборке**, поэтому после их изменения нужен передеплой.

### 8. Шрифты для OG обязательно коммитить

`assets/fonts/*.ttf` нужны при сборке. Если добавить их в `.gitignore`
«как бинарники», деплой упадёт на генерации OG-картинки.
